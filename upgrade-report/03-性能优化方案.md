# 03 性能全面优化方案

## 1. 性能基线（2026-08-04，本机 PHP 内置服务器）

| 指标 | 基线 | 说明 |
| --- | ---: | --- |
| 首页 HTML | 302 ms / 39.5 KB | `GET /`（Accept: text/html） |
| 单条解析 | 759 ms / JSON 约 1 KB | 抖音真实视频 `POST /` |
| 前端资源 | 无外部 CSS/JS | 全部内联，无 bundle 体积问题 |
| 批量解析 | 顺序执行，耗时约 N × 单条 | 当前无并发 |
| 重复解析 | 无缓存 | 相同链接每次重新请求平台接口 |

## 2. 优化清单

| 优先级 | 优化项 | 当前问题 | 方案 | 预期收益 |
| --- | --- | --- | --- | --- |
| P0 | 解析结果缓存 | 相同视频重复解析 759ms | `storage/cache/` 按平台+ID 缓存，TTL 24h | 重复解析降至约 20-50ms |
| P1 | 批量并发 | 顺序解析慢 | 前端按 3-4 并发提交；服务端可加队列 | 批量耗时降为约 1/3 |
| P1 | a_bogus 进程开销 | 每次解析都 `proc_open` Node | 进程内签名缓存/长驻 Node 服务；失败降级 | 抖音解析减少 100-300ms |
| P1 | HTTP 缓存头 | 静态 HTML 无缓存策略 | `Cache-Control`、`ETag`；媒体代理透传缓存头 | 重复打开首页降低延迟 |
| P2 | 压缩传输 | 内置服务器未开压缩 | Nginx/Apache 部署时启用 gzip/brotli | HTML 传输减少 60-70% |
| P2 | 媒体代理 | 固定 64KB buffer | 按 Range 动态分块、连接复用 | 拖动进度条更流畅 |
| P2 | 限流存储 | 文件 JSON 每次请求读写 | 目录分片或 Redis 可选后端 | 高并发下减少 IO 竞争 |
| P3 | 部署形态 | PHP 内置服务器仅适合开发 | Docker + Nginx + PHP-FPM | 生产可用、QPS 提升 |

## 3. 实施要点

1. 缓存键使用规范化的平台 + 视频 ID，缓存文件附带过期时间与来源 URL。
2. 批量解析在前端 `Promise.all` 分段限流，避免触发限流。
3. Node 签名改为“首次启动校验，命中后复用”，并把失败回退路径（`fetchLegacy`）保留。
4. 部署到生产环境后再补 Lighthouse 与接口压测，目标：Performance ≥ 90、接口 P99 < 1s。

## 4. 预计排期

| 阶段 | 内容 | 预估工时 |
